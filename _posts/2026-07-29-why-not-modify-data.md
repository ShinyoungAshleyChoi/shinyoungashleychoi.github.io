*PostgreSQL, Kafka, Iceberg 그리고 Git이 같은 철학을 선택한 이유*

Iceberg는 Parquet 파일을 수정하지 않는다.  
PostgreSQL은 UPDATE를 하지 않는다.  
Kafka는 메시지를 삭제하지 않는다.  
Git은 Commit을 수정하지 않는다.

처음 보면 이상하게 들린다. 데이터베이스는 데이터를 수정해야 하고, 메시지 큐는 메시지를 읽으면 삭제해야 하며, 파일은 저장하면 덮어써지는 것이 당연하다고 생각하기 때문이다.

하지만 현대의 많은 시스템은 정반대의 선택을 한다. 기존 데이터를 수정하는 대신 **새로운 사실을 기록(Add/Append)** 한다.

PostgreSQL은 새로운 Row를 만들고, Kafka는 새로운 Event를 추가하며, Iceberg는 새로운 Snapshot을 생성하고, Git은 새로운 Commit을 쌓는다.

서로 해결하는 문제도, 사용하는 분야도 다르다. 그럼에도 이들은 놀라울 정도로 같은 설계 철학을 공유한다.

**"수정(Mutate)하지 말고, 기록(Append)하라."**

이 글에서는 PostgreSQL, Kafka, Iceberg, Git이 왜 모두 이 철학을 선택했는지, 그리고 이 선택이 동시성, 안정성, 복구, 그리고 시스템 설계에 어떤 영향을 주는지 살펴보려 한다.

---

## 우리는 왜 '수정'이 당연하다고 생각할까?

프로그래밍을 처음 배우면 '수정'은 너무나 자연스럽다.

```sql
UPDATE users
SET age = 30
WHERE id = 1;
```

이 SQL을 실행하면 대부분의 사람은 머릿속으로 이렇게 상상한다.

> "기존 데이터가 30으로 바뀌었겠지."

텍스트 파일도 마찬가지다.

저장(Save) 버튼을 누르면 기존 내용이 새로운 내용으로 덮어써질 것이라고 생각한다.
메시지 큐 역시 메시지를 읽으면 큐에서 사라지는 것이 자연스럽다.
우리에게 '수정'은 너무 익숙한 개념이다.
그런데 시스템이 커질수록 이 단순한 방식은 여러 문제를 만들기 시작한다.

---

## 수정은 생각보다 위험하다

만약 두 명의 사용자가 동시에 같은 데이터를 수정한다면 어떻게 될까?

누가 마지막에 저장했는가?

이전 값은 무엇이었는가?

왜 값이 변경되었는가?

실수로 잘못 수정했다면 이전 상태로 돌아갈 수 있을까?

읽고 있는 도중 다른 사용자가 데이터를 수정하면 내가 보고 있는 데이터는 무엇을 기준으로 해야 할까?

메시지를 한 번 읽고 삭제해 버렸는데, 나중에 버그가 발견되면 어떻게 다시 처리할 수 있을까?

Parquet 파일을 직접 수정하는 도중 작업이 실패하면 파일은 어떤 상태가 될까?

Git에서 과거 Commit이 계속 바뀐다면 협업은 가능할까?

결국 문제는 하나다.

**기존 상태를 덮어쓰는 순간, 과거는 사라진다.**

그리고 시스템은 과거를 잃는 순간부터 복잡해지기 시작한다.

---

## 그래서 현대 시스템은 다른 선택을 했다

흥미롭게도 서로 전혀 다른 분야의 시스템들은 같은 결론에 도달했다.

| 시스템 | 기존 방식 | 실제 선택 |
| --- | --- | --- |
| PostgreSQL | Row 수정 | 새로운 Row 생성 |
| Kafka | 메시지 삭제 | 새로운 Event 추가 |
| Iceberg | 파일 수정 | 새로운 Snapshot 생성 |
| Git | Commit 수정 | 새로운 Commit 생성 |

이들은 모두 기존 데이터를 수정하지 않는다.

대신 **새로운 상태를 추가(Append)** 한다.

과거는 그대로 남겨 두고, 현재는 새로운 기록으로 표현한다.

---

## PostgreSQL은 UPDATE를 하지 않는다

PostgreSQL에서 UPDATE를 실행하면 실제로는 기존 Row를 덮어쓰지 않는다.

기존 Row는 그대로 남겨 두고 새로운 Row를 생성한 뒤, 이전 Row는 더 이상 사용되지 않는 상태(dead tuple)로 표시한다.

처음에는 꽤 비효율적으로 보인다.

'그냥 값을 바꾸면 되는데 왜 굳이 새로운 Row를 만들지?'

하지만 이 방식 덕분에 PostgreSQL은 별도의 Lock을 최소화하면서도 여러 사용자가 동시에 같은 테이블을 읽고 쓸 수 있다.

바로 MVCC(Multi-Version Concurrency Control)다.

그리고 더 이상 필요 없는 이전 Row는 나중에 VACUUM이 정리한다.

즉, **수정하지 않고 기록한 뒤, 나중에 정리한다.**

---

## Kafka는 메시지를 삭제하지 않는다

전통적인 메시지 큐는 메시지를 읽으면 삭제한다.

하지만 Kafka는 다르다.

Kafka는 메시지를 읽어도 삭제하지 않는다.

Consumer는 단지 "나는 여기까지 읽었다"라는 Offset만 기록한다.

덕분에 Consumer는 언제든지 과거 Event를 다시 읽을 수 있다.

버그가 발생하면 처음부터 다시 처리(Replay)할 수 있고, 새로운 Consumer를 추가해도 기존 Event를 그대로 활용할 수 있다.

Kafka가 관리하는 것은 "누가 읽었는가"가 아니라 "무슨 일이 발생했는가"이다.

---

## Iceberg는 Parquet 파일을 수정하지 않는다

수십 GB의 Parquet 파일을 직접 수정하는 것은 매우 위험하다.

작업 도중 실패하면 파일이 손상될 수도 있고, 여러 사용자가 동시에 접근하는 환경에서는 일관성을 유지하기도 어렵다.

그래서 Iceberg는 기존 파일을 수정하지 않는다.

새로운 Parquet 파일을 생성한 뒤, 새로운 Snapshot이 이 파일들을 가리키도록 메타데이터만 교체한다.

덕분에 특정 시점의 데이터로 되돌아가는 Time Travel도 가능해진다.

기존 파일은 나중에 Snapshot Expiration이나 Compaction 과정에서 정리된다.

---

## Git도 마찬가지다

많은 개발자가 매일 Git을 사용하지만, Git 역시 같은 철학을 따른다는 사실은 의외로 잘 의식하지 않는다.

Git에서 Commit은 수정되지 않는다.

새로운 작업을 하면 새로운 Commit이 만들어지고, Branch 역시 Commit을 가리키는 포인터만 이동한다.

그래서 언제든 과거 Commit으로 돌아갈 수 있고, Branch를 만들어 다른 방향으로 작업을 이어 갈 수도 있다.

Git은 파일의 현재 상태보다 **변화의 역사**를 더 중요하게 생각한다.

---

## 결국 모두 같은 문제를 해결하고 있었다

지금까지 살펴본 네 시스템은 서로 해결하는 문제가 다르다.

PostgreSQL은 데이터베이스다.

Kafka는 메시지 브로커다.

Iceberg는 데이터 레이크 포맷이다.

Git은 버전 관리 시스템이다.

하지만 이들은 모두 하나의 질문 앞에서 같은 답을 선택했다.

> **"기존 상태를 덮어쓰는 것이 정말 최선일까?"**

그리고 모두 같은 결론에 도달했다.

**수정하지 말고, 새로운 사실을 기록하자.**

이 선택 하나로 동시성은 쉬워졌고, 장애 복구는 강력해졌으며, 과거를 추적할 수 있게 되었고, 시스템은 더 안전해졌다.

---

## 마치며

예전에는 PostgreSQL의 MVCC, Kafka의 Log, Iceberg의 Snapshot, Git의 Commit을 각각 별개의 기술이라고 생각했다.

하지만 하나씩 공부할수록 오히려 반대라는 생각이 들었다.

이들은 서로 다른 기술이 아니라, 같은 철학을 각자의 문제에 맞게 구현한 시스템이었다.

기술은 계속 변한다.

하지만 좋은 설계는 반복된다.

그리고 현대 시스템이 반복해서 선택한 설계는 의외로 단순하다.

**과거를 지우지 말고, 새로운 사실을 기록하라.**
